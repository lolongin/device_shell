# AI Device Gateway Design

## Goal

Provide an execution intermediary between AI agents and devices via MCP protocol. The gateway turns the AI's frequent single-command executions into high-level, reusable device operations: it manages connections, executes commands/batches/scripts, returns summarized results with deferred raw output retrieval, runs parameterized automation flows (sequential / dependency / wait-for-condition / timeout-retry), and reuses repeated flows via "skills". It runs on the PC/app side, requires no device-side Linux modification, and supports generic Linux + network devices.

## Scope

- Add an `ai_*` tool namespace to the existing `device_tui` FastMCP server (new file `src/device_mcp/tools/ai_gateway.py`). MCP tools are thin forwards; real logic lives in a new `src/ai_gateway/` package on the app side.
- Reuse the existing execution stack: session lifecycle (device tabs), `TerminalExecutionRunner`/`build_batch_plan`, file transfer, approval/audit/idempotency, device discovery. Do not build a parallel execution stack.
- Add a results semantic layer: deterministic `summary` + `result_id` deferred raw-output retrieval via `ai_get_result`.
- Add a flow orchestration layer (`FlowEngine`) and a skill registry (`SkillRegistry`).
- Add device→PC download (`ai_download_file`) — the one capability currently missing from the file-transfer direction.
- Do not change existing `terminal_*` tool semantics (backward compatibility for already-connected agents).

### Explicitly out of scope

- New UI panels (skill editor, result browser). Skill definitions are files; results are queried via MCP tools. UI can be a separate future project.
- Conditionals/branches/loops inside flows, cross-step variable passing, parallel steps. Flows are sequential orchestration + condition gating + bounded retry.
- LLM-based summarization. Summaries are deterministic local rules — repeatable, testable, no token cost.
- A separate MCP server deployment unit. The gateway shares the existing `device_tui` server.

## Architecture

### Component layout

```
ai_* tools (device_mcp/tools/ai_gateway.py)
  → McpGateway.call
  → AppControlClient (device_mcp/client.py)
  → AppControlHttpServer → AppControlService.handle_tool (device_mcp/service.py)
  → execute_ai_device_action (src/app/ai_device_ops.py handler dict, new ai_* branches)
  → AiDeviceOpsMixin._execute_ai_gateway_* handlers
  → GatewayService (src/ai_gateway/service.py)
       ├── ResultStore   (src/ai_gateway/result_store.py)
       ├── FlowEngine    (src/ai_gateway/flow_engine.py)
       └── SkillRegistry (src/ai_gateway/skills.py)
```

Every `ai_*` action flows through the existing risk classification, `approval_token` gate, `idempotency_key`, and audit logging unchanged. Multi-command/flow actions additionally carry a sub-step manifest in the audit record (step count, command count) so the operator knows how many device operations one gateway call expands to.

### Reuse boundaries

| Concern | Reused from | Changed |
| --- | --- | --- |
| Session lifecycle | existing device tabs / session layer | no |
| Single/batch execution | `TerminalExecutionRunner`, `build_batch_plan` | no |
| File transfer | `file_transfer_start` (PC→device) | no; `download_file` (device→PC) is new |
| Approval/audit/idempotency | `AppControlService` risk gates | no |
| Device discovery | `ai_device_snapshots` / repository | no |

New capability is exactly three things: result summarization + `result_id`, flow orchestration, skill reuse — plus the `download_file` direction.

## MCP Interface (v1)

Eight tools registered under the `ai_*` namespace:

| Tool | Args | Returns |
| --- | --- | --- |
| `ai_create_session` | `device_id` | `{session_id, connected}` |
| `ai_execute_command` | `session_id, command, timeout_seconds` | `{result_id, summary}` |
| `ai_execute_batch` | `session_id, commands[], command_timeout_seconds` | `{result_id, summary}` |
| `ai_execute_script` | `session_id, script, shell?, timeout_seconds` | `{result_id, summary}` |
| `ai_upload_file` | `device_id, source_path, destination_path` | `{result_id, status}` |
| `ai_download_file` | `device_id, source_path, destination_path` | `{result_id, status}` |
| `ai_get_result` | `result_id, include_raw` | `{result, raw_output}` |
| `ai_run_skill` | `skill_name, params, timeout_seconds` | `{result_id, summary}` |

- `session_id` is the existing session identifier (reused lifecycle; `ai_create_session` maps to / reuses an existing device tab).
- `result_id` is generated by the unified `ResultStore`.
- `ai_execute_script` semantics: the multi-line body is injected as a single execution unit. On Linux (SSH) it is written to the shell and run as one block, so variables/loops/`if` across lines work; on network devices (Telnet/VRP) the lines are executed as a command sequence with per-line prompt waits, since there is no shell to hold a script. This is the one place where a network device cannot accept the script as an atomic unit; the same `{result_id, summary}` contract still applies.
- `ai_execute_command/batch/script`, `ai_upload_file/download_file`, and `ai_run_skill` accept an optional `idempotency_key` (existing idempotency cache).

### Call flow (ai_execute_command example)

```
1. ai_execute_command(session_id, command, timeout_seconds)
2. MCP → AppControlService.handle_tool → risk classification + approval gate
3. approved → action kind="ai_execute_command" → AiDeviceOpsMixin handler
4. handler → GatewayService.execute_command(session_id, command, timeout)
5. GatewayService reuses existing session/terminal: locate device tab →
   TerminalExecutionRunner runs the single command
6. raw output into ResultStore → deterministic summary
7. return {result_id, summary}
8. AI needs detail → ai_get_result(result_id, include_raw=true)
```

## Result Contract

All `ai_execute_*` and `ai_run_skill` return the same shape:

```json
{
  "result_id": "R7f3a",
  "summary": {
    "status": "success",
    "exit_code": 0,
    "command_count": 1,
    "error_count": 0,
    "important_lines": [],
    "duration_ms": 1234
  },
  "response_time_ms": 40
}
```

- `status`: `success | failed | timeout | interrupted`.
- `error_count` / `important_lines`: produced by deterministic rules in `ResultStore.summarize_output()` — scan for error/failure keywords (e.g. `error`, `failed`, `%`-prefixed Syslog lines); if none match, take the tail N lines. No LLM involved.
- `duration_ms`: wall-clock execution duration.
- `response_time_ms`: MCP round-trip overhead, distinct from `duration_ms`.

### result_id lifecycle (ResultStore)

- In-memory ring buffer, max 500 entries, LRU eviction.
- TTL 24h, cleaned by a timer.
- `result_id` format: `R` + short random suffix (secret-safe, idempotency-key style).
- `ai_get_result(result_id, include_raw)`: `include_raw=false` returns only `{result, summary}`; `true` appends `raw_output` (may be long — caller bears token cost).

## Error Handling

Follow the existing `AppControlError` pattern (`code` + Chinese message + HTTP status). A timeout is **not** an error — it is a normal outcome with `summary.status = "timeout"` and a `result_id`; `ai_get_result` retrieves whatever output was produced before the deadline. Hard errors:

| Condition | Code | Status | Behavior |
| --- | --- | --- | --- |
| Session/device unavailable | `session_unavailable` | 409 | prompt to re-run `ai_create_session` |
| Approval rejected | `approval_required` | 409 | existing approval flow with `approval_token` |
| Flow step failure | `flow_step_failed` | 422 | after retry policy exhausted; carries failing step number + `result_id` pointing at that step's output |

Idempotency: `ai_execute_command/batch/script`, `ai_upload_file/download_file`, `ai_run_skill` all accept `idempotency_key` through the existing cache.

## Flow Engine

A flow is a first-class orchestration unit — a step list with dependencies, wait conditions, and bounded retry. Execution delegates to the existing `TerminalExecutionRunner`; the flow engine only resolves dependencies (DAG), polls conditions, and orchestrates retries.

### Flow data structure (JSON, shared with Skill templates)

```json
{
  "steps": [
    {"id": "s1", "command": "display version", "timeout_seconds": 30},
    {"id": "s2", "command": "display cpu", "depends_on": ["s1"]},
    {"id": "s3", "command": "save", "retry": {"max": 2, "interval_ms": 3000, "on_status": "failed"}}
  ],
  "wait_conditions": {
    "s2": {"type": "command_output_contains", "command": "display version",
           "expected": "VRP", "interval_ms": 2000, "max_attempts": 15}
  }
}
```

### Execution semantics

- `depends_on` → a step runs only after its prerequisites complete. Currently only "prior step completed" is supported — no variable passing between steps (YAGNI; avoids the flow engine degrading into a branching interpreter).
- `wait_conditions` → before a gated step runs, poll the condition command until it matches; exceed `max_attempts` → step fails.
- `retry` → retry only on execution failure (`on_status: failed`). Timeout / condition failures are not retried (ambiguous semantics, can mask a wedged device); retry interval is configurable.

### Explicitly not done (YAGNI red line)

Conditional branching / loops, cross-step variable passing, parallel steps. Flow is sequential orchestration + condition gating + bounded retry.

## Skill Reuse

`SkillRegistry` loads `src/ai_gateway/skills/*.json` — each file is a Flow template plus parameter placeholders:

```json
{
  "name": "driver_reload",
  "description": "重载设备驱动（用于变更验证）",
  "params": [{"name": "device_id", "type": "string", "required": true}],
  "flow": { "steps": [] }
}
```

- `run_skill("driver_reload", params)` → parameter substitution (`${device_id}` placeholders) → instantiate a Flow → hand to `FlowEngine`.
- One bundled example skill (`driver_reload`); operators add hand-written JSON files, scanned at registry startup.
- Skills and flows share the same structure — one engine, two entry points (direct `ai_execute_*` for single commands, `ai_run_skill` for templated flows).

## Approval / Audit Integration

- Each `ai_*` tool registers on `McpGateway` and flows through `AppControlService.handle_tool`, so risk classification, `approval_token` gating, `idempotency_key`, and audit logging (with command-text redaction) apply automatically.
- Risk classification reuses `classify_command_risk()`:
  - `ai_execute_command/batch/script` → classify the command text.
  - `ai_run_skill` → classify all step commands after skill expansion, take the highest.
  - `ai_upload_file` → MEDIUM; `ai_download_file` → LOW (by direction).
- New audit dimension: multi-command / cross-direction actions (`ai_execute_batch`, `ai_execute_script`, `ai_run_skill`, `ai_download_file`) carry a **sub-step manifest** in the audit record (step count, command count) so operators know how many device operations one call expands to. This is an additive field on the existing action record, not a new mechanism.

## State Persistence

- `DesktopStateMixin`, `DESKTOP_STATE_VERSION` 14 → 15.
- New `ai_gateway` section storing only configuration, not result bodies:

```json
{
  "ai_gateway": {
    "result_store": {
      "max_entries": 500,
      "ttl_hours": 24
    }
  }
}
```

- Result bodies stay in memory (lost on restart) — device output should not be persisted to disk. Config values are clamped (e.g. `max_entries` 50–5000, `ttl_hours` 1–168).
- Skill definitions are files, not desktop state — versioned with git.

## Implementation Notes

- New package `src/ai_gateway/` with four files: `service.py`, `result_store.py`, `flow_engine.py`, `skills.py`.
- `GatewayService` is a facade holding `ResultStore`, `FlowEngine`, `SkillRegistry`; it exposes high-level methods for the mixin handlers.
- New MCP tool module `src/device_mcp/tools/ai_gateway.py`; register in the same way as the existing tool modules (see `register_transfer_tools` pattern).
- Handler dictionary in `src/app/ai_device_ops.py` gains `ai_*` branches; risk/approval/audit run before the handler.
- The flow engine's step execution reuses `TerminalExecutionRunner`/`build_batch_plan` without modification; each step's output goes into `ResultStore`.
- Audit sub-step manifest is an additive field on the existing action record.

## Acceptance Criteria

- `ai_create_session` reuses/creates a device session; `ai_execute_command/batch/script` run through the existing stack and return `{result_id, summary}`.
- `ai_get_result` returns summarized and (optionally) raw output by `result_id`, with 24h TTL and LRU eviction.
- `ai_download_file` transfers device→PC.
- `ai_run_skill` instantiates a templated flow, substitutes parameters, and executes with dependency/wait/retry semantics.
- Every `ai_*` tool passes through existing risk classification, approval, idempotency, and audit (with sub-step manifest for multi-command actions).
- Existing `terminal_*` tools are unchanged and still work.
- Full test suite passes.
